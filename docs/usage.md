# Usage page

The sidebar footer's **Usage** button opens the `/t3sidebar-usage` page (and, clicked again while it is shown, closes it to bring back the session or new-session draft it covered; the **Limits** button works the same way, and switching from one page to the other still returns to what was there before either opened), modeled on T3 Code's Usage page and on the quota chart of Theo's CLIProxyAPI fork ("These 3 skills changed my life", https://www.youtube.com/watch?v=5Bmp9cz1JN8&t=496).

## Usage tab

Three charts on one time axis: tokens, API-equivalent cost and human user messages. 24 h covers the last 24 hours in 144 ten-minute buckets; 7, 30 and 90 days cover whole local days, today included, in hourly, six-hour and daily buckets from local midnight (in the Desktop client's time zone), at most 168, 120 and 90 of them. Every period ends with the bucket in progress. Every chart plots the amount in each bucket, not a rate, so the bucket size is the chart's unit; a DST day stretches or shrinks one bucket by an hour, and that bucket holds an hour more or less of usage. Tooltips give each series' amount in the hovered bucket and their total. **Split** draws one series per provider or per model (a model served through several providers is one series); **Mode** stacks the series or draws them independently from zero.

- Source: Hermes `session_model_usage` (exact totals per session × model × task), read strictly read-only through `GET /usage/history` (`usage_history.py`). No extra data is stored.
- Timing: Hermes keeps no per-call token counts, so each total is spread over the calls that produced it. A main-loop row is spread over the session's assistant messages (one per API call) between its first and last recorded call: input, cache-read and cache-write tokens in proportion to the context at each call, that is everything the session stored before it, and output tokens in proportion to the reply's size. Sizes count message text, tool calls and reasoning, in stored bytes (characters on SQLite before 3.43). Auxiliary rows, such as title generation, and rows without matching messages are spread evenly between their first and last call. Totals are exact; their placement in time is approximate.
- Cost: every row is priced at the list price of the API it corresponds to (`openai-codex` → `openai`), including subscription traffic that Hermes records as $0 "included". Models without a known price count as $0 and are named under the charts.
- User messages: only messages typed by a person. Cron, internal and delegated subagent sessions are excluded (subagents often keep the parent's `desktop`/`tui` source, so they are identified by Hermes's `_delegate_from` marker), as are notifications Hermes injects into the user role.

## Limits tab

The sampler belongs to the loaded agent plugin in each profile. Disabling or unloading that plugin stops future sampling, and late polls cannot restart it; re-enabling creates a new owner. Unload waits up to five seconds for a tick already collecting, which may finish afterward. Closing Desktop alone does not unload the backend plugin.

For each provider, a pooled chart sums every pool account's remaining percentage for one window (5-hour, weekly or a model-scoped window). The Window selector names model-scoped windows `Model limit #1`, `#2`… in its order; the account bars name the model. OpenAI providers are drawn in light grey, other providers in a hue of their own. Past samples are drawn as a solid area, then comes a **Now** line and a dashed projection. The projection drains at the pooled rate over the averaging period, twelve hours by default and adjustable from one hour to 30 days with the pencil beside a chart's averaging label (one setting for every chart): the drops between consecutive readings of every account, divided by the time those readings cover, using whatever history exists when it is shorter. It uses accounts in pool priority order, and steps up when an account's window resets. Under each chart, a folded **Accounts** card previews the account names; unfolded, it holds one card per account showing its pool priority, plan and each window with a pace tick and its reset time. Anthropic reports no window durations, so its 5-hour and weekly windows (model-scoped ones included) take the durations their names imply, which also places their pace ticks.

On both tabs the controls bar stays fixed at the top while the charts scroll beneath it; its refresh icon spins while a refresh is in flight.

- Source: `GET /usage/limits` (`usage_limits.py`) reads samples from `<HERMES_HOME>/plugin-data/hermes-t3sidebar/usage-limits.sqlite3`, kept for 35 days.
- Wire format: each account window's history is one series of parallel arrays (`t`, `remaining_percent`, `resets_at`) in whole seconds and one-decimal percentages, keeping only both ends, every change of value or reset time and the sample just before each change. Unchanged readings carry no information for the step chart, so the live history measured 17× smaller than one object per sample (623 KB to 36 KB); the drain average counts an unchanged stretch that straddles the lookback start from that start.
- Sampling: a backend thread wakes every 5 minutes. It fetches each pool account's usage concurrently with that account's own token, then records the readings: a Codex account through Hermes's public `fetch_account_usage` in read-only mode, as Hermes's model picker does; an Anthropic account with one GET of its own (below). That fetch never refreshes or rotates tokens, clears cooldowns or redeems banked resets, and leaves Hermes's own single-account usage untouched. Like Hermes's model picker, credentials sharing a token on the same route are read once, and Codex credentials whose ChatGPT tokens decode to the same account on the same route are shown once; one key on two routes, such as two proxies sharing a password, stays two accounts. The thread starts on the first Desktop poll after a backend start and keeps sampling while Desktop is closed. Only `openai-codex` and `anthropic` credential-pool entries are sampled. A vetted provider whose pool is empty is shown as logged out, except Anthropic: with an empty Hermes pool it falls back to Claude Code's own login on the host (`$CLAUDE_CONFIG_DIR` or `~/.claude`), the account the Claude Code-based provider plugin actually consumes. Its plan comes from Anthropic's OAuth profile `rate_limit_tier`, read at the sampler's first collection after Hermes starts, then hourly; a failed read keeps the last plan and is retried after 15 minutes.
- Anthropic usage: each Anthropic account (pool entry or Claude Code login) is read with a single GET of `api.anthropic.com/api/oauth/usage?cedar_ember=1&skip_spend=1` sent by the plugin with that account's token, never stored. Hermes's own fetch hits the same URL but keeps only the 5-hour and weekly windows; model-scoped limits, such as a weekly cap on Fable, are only in the body's `limits` list and resets only in its `cedar_ember` block, so reading through Hermes as well would send the same GET twice. The plugin maps the windows as Hermes does (same labels, so the same window keys as samples recorded through Hermes), taking `utilization` as the percent Anthropic sends, then adds the model-scoped ones (`weekly:fable`). As in Hermes, a Console API key (`sk-ant-api…`) is never sent to that OAuth endpoint and reads as having no limits. The reading no longer lands in Hermes's in-memory Anthropic usage; Hermes's own reads (model picker, `/usage`) keep it. A failed read fails that account's sample. An expired Claude Code token is refreshed by calling Hermes's public `fetch_account_usage` without a token: Hermes then resolves one through the Claude Code resolver its Anthropic calls use, which writes the new token back to Claude Code's credentials; the sampler then reads the file again. A failed refresh shows the account as expired, as does an Anthropic API key in Hermes's environment, which that resolver returns instead of refreshing the login.
- Banked resets: Codex's usage response only counts banked reset credits, so at most once an hour the sampler also reads Codex's credit list (`/wham/rate-limit-reset-credits`, read-only). By default it reads the list of the Codex account Hermes is currently using, through Hermes's `credentialed_provider_request` (declared with `requires_auth: [openai-codex]`): Hermes attaches its own sign-in and the plugin never sees the token. That response does not name the pool account, so with one Codex account in the pool the list goes under that account, and with several it is shown first under **Accounts** as **Current account**, while the other accounts show only their count. The experimental setting **Banked reset expiries for every Codex account** (Experimental section of the plugin's settings page, off by default, kept in the plugin's Limits store) lists every pool account instead, each with its own token through Hermes internals that may change in any release (a 401 is not refreshed); if those internals are gone, the default applies and the setting's switch is disabled with an *Incompatible with your Hermes version* note. Only each credit's status, grant and expiry times are stored, plus how many could be redeemed right now, and switching the setting drops the other mode's lists. The sampler never redeems anything. Credits are listed soonest expiry first.
- Using a banked reset: Codex picks which credit is spent, so the **Use one** button belongs to the account, right of its credit list. It is green once any account-wide allowance has less than 80% left, OpenAI's manual redeem rule ([How resets work in Codex](https://help.openai.com/en/articles/20001498-how-resets-work-in-codex)); otherwise it is dashed and padlocked with `all ≥80% left`, and does nothing. While a green button is hovered or focused, each account-wide bar of that account shows the share the reset would give back, hatched in the bar's own colour. Codex's own redeemable count follows the stricter rule for the assistant (10% or less left), so it is not used. The confirmation shows the share of the weekly allowance left now, which the reset discards (the 5-hour remainder is worthless once weekly is empty), with its units. Confirming calls `POST /usage/limits/redeem` (`banked_reset.py`), which runs Hermes's own `/usage reset --force` with that pool entry's credential, then runs a collection right away so the page shows the restored allowance. As with `/usage reset`, a successful reset lets Hermes clear its Codex pool cooldowns, and a 401 makes Hermes refresh that credential once. Only the outcome code goes back to the page; a refusal (`nothing_to_reset`) keeps the credit.
- Anthropic limit resets: Anthropic lists an account's resets (5-hour, weekly, Fable, full) only in the `cedar_ember` block of its usage response, and only to Claude Code. The sampler's Anthropic usage GET asks for that block and names itself as the Claude Code CLI installed on the host (`claude-cli/<version> (external, cli)`, from `claude --version`, as T3 Code does); without a CLI it is named as Hermes's own Anthropic usage fetch (`claude-code/2.1.0`) and no resets are listed. The plan's profile read is always named `claude-code/2.1.0`, so no Anthropic request goes out under httpx's name. Each reset is grouped as Claude Code does (one that gives back weekly usage is a Fable reset, else its declared type, else what it clears) and stored with its id, count, expiry, whether Anthropic accepts it now and the limits it clears; a list older than 15 minutes is not offered. Each reset gets its own line and **Use one** button, padlocked with Anthropic's reason when it would refuse it. Hovering the button hatches what that reset gives back: the limits it clears refill, and a Fable reset also refills Fable's own window and gives back only Fable's share of the weekly one. The confirmation shows the share of the window it refills that is lost (Fable's window for a Fable reset, the 5-hour one for a 5-hour reset, else the weekly one). Confirming calls `POST /usage/limits/redeem` with the reset's id, which sends Claude Code's own claim, `POST /api/organizations/<organization>/reset_rate_limits` (`program: cedar_ember`, the reset id and a request id), with the account's token and the same User-Agent; it never refreshes a token. A claim whose answer never arrived (or that Anthropic answers `unavailable`) locks the account's resets until a newer reading, and the next attempt on that reset reuses its request id, so Anthropic answers `already_used` rather than spending a second one.
